# DeshRide backend (Supabase)

DeshRide runs in two modes:

- **On-device demo mode.** No configuration. Everything is stored on the one phone, as before. Good for demos and for the test suite.
- **Shared mode.** Set two build variables and every phone shares rides, bookings, chat and notifications through a Supabase project.

The app code is the same in both modes. Pages call `src/lib/store.ts` as before. In shared mode, `src/lib/backend/sync.ts` keeps the store's local copy in step with the database, and every change is checked by the server.

## What runs where

| Piece | File | Notes |
|---|---|---|
| Tables | `supabase/migrations/0001_schema.sql` | Phone, NIDs, plate and payout wallet live in `profiles_private`, which only the owner can read. |
| Who can read what | `supabase/migrations/0002_rls.sql` | Row-level security. Every table refuses direct writes. |
| Contact guard | `supabase/migrations/0003_guard.sql` | Generated by `scripts/gen-guard-sql.py`. It mirrors `src/lib/contactGuard.ts`. |
| Booking rules | `supabase/migrations/0004_functions.sql` | All writes run as Postgres functions: seat checks under a row lock, blocks, expiry, refunds, no-shows, ratings, chat. |
| Background jobs and live updates | `supabase/migrations/0005_cron_realtime.sql` | A `pg_cron` sweep runs every 5 minutes (expire requests, release fares, send trip reminders). Live updates use Supabase Realtime. |
| Demo rides | `supabase/seed.sql` | Five rides from clearly marked demo drivers. Re-run it to refresh their dates. |
| App side | `src/lib/backend/` | `client.ts` (connection), `mappers.ts` (rows ↔ app types), `sync.ts` (sign-in, pull, live updates, writes). |

## Set up a free project (one time, about 10 minutes)

1. **Create the project.** Go to <https://supabase.com>, sign up (no card needed), and choose **New project**.
   - **Region:** Southeast Asia (Singapore), the closest to Dhaka.
   - **Database password:** save it somewhere safe.
2. **Allow automatic sign-in.** Go to **Authentication → Sign In / Providers** and turn on **Allow anonymous sign-ins**. Each phone then gets an account automatically on first open.
3. **Run the database files.** Either:
   - **SQL Editor:** open each file in `supabase/migrations/` in order (`0001` … `0005`), paste it into **SQL Editor** and press **Run**. Then do the same with `supabase/seed.sql`.
   - **CLI:** run these one at a time:
     ```bash
     npx supabase@2.121.0 login
     ```
     ```bash
     npx supabase@2.121.0 link --project-ref <your-project-ref>
     ```
     ```bash
     npx supabase@2.121.0 db push --include-seed
     ```
4. **Turn on the scheduler.** Go to **Database → Extensions**, find **pg_cron** and enable it, then run `0005_cron_realtime.sql` again. It schedules the sweep only when pg_cron is available.
5. **Copy the keys.** Go to **Project Settings → API** and copy the **Project URL** and the **anon public** key. The anon key is meant to be public: row-level security decides what each user can see.
6. **Tell the app.** Do whichever you need:
   - **Local development:** copy `.env.example` to `.env.local` and fill both values.
   - **GitHub builds (APK and Pages):** go to **Settings → Secrets and variables → Actions** in the GitHub repo and add `SUPABASE_URL` and `SUPABASE_ANON_KEY`.

### Free plan limits

The free plan gives a 500 MB database, 50,000 monthly users and 2 projects.

**A free project pauses after 7 days with no traffic.** Press **Restore** in the dashboard to wake it. It also has no automatic backups. Move to the US$25/month plan once real riders depend on it.

## Checking the database locally

`supabase/tests/run.sh` applies every migration to a throwaway Postgres database and checks:
- privacy rules;
- refused direct writes;
- chat censoring, including numbers split across messages;
- blocks, expiry, ratings and segment fares;
- 4 riders racing for the last seat (exactly one wins).

Run it against any disposable Postgres 15+:

```bash
supabase/tests/run.sh "psql -h localhost -p 5432 -U postgres"
```

With Docker you can run the whole stack locally (`npx supabase@2.121.0 start`). The app then talks to `http://127.0.0.1:54321` using the anon key that `supabase status` prints.

## What is still simulated

- **Payments.** Escrow states (`held → releasing → released/refunded`) are enforced by the server, but no money moves yet. The bKash/Nagad aggregator from `docs/feasibility/05` plugs into `request_booking`, `update_booking_status` and the sweep.
- **SMS login codes.** Sign-in is anonymous per phone for now. Real OTP needs a BTRC-enlisted SMS aggregator (`docs/feasibility/03`). Supabase phone auth then replaces `signInAnonymously` in `sync.ts`.
- **Push notifications.** They show in the app through live updates. Phone push (FCM) can be added later from a database webhook.
- **Photos** are small data URLs in the profile row. Move them to Supabase Storage before launch.

## Moving to AWS later

The database is plain Postgres. The Supabase-specific parts are fenced in:

1. **Identity.** `auth.uid()` is used only inside `app.current_user_id()` (`0002_rls.sql`). On AWS, point that function at the user id from a Cognito JWT that your API verifies, for example `current_setting('request.jwt.claim.sub', true)` set per request.
2. **Data.** Run `pg_dump` on the Supabase database and `pg_restore` it into **RDS for PostgreSQL** in `ap-south-1` (Mumbai, the closest AWS region to Bangladesh). Enable `pg_cron` in the RDS parameter group, or call `app.sweep_lifecycle()` from a scheduled Lambda every 5 minutes.
3. **API and live updates.** Either:
   - run **self-hosted Supabase on EC2**, so the app needs no change; or
   - put a small API (Lambda or App Runner) in front of RDS that exposes the same function names, and swap Realtime for AppSync or API Gateway WebSockets.

   Only `src/lib/backend/client.ts` and `sync.ts` change on the app side.
